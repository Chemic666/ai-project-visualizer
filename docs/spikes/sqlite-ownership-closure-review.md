## A. Closure Scope

The question answered is whether the disposable cooperative implementation, under its tested local binding and private connection lifetime, demonstrates actual same-file cross-process Owner exclusion, separate Project fencing, guarded fixture commits, controlled loss/crash handling, and explicit recovery without PID/heartbeat/timeout takeover.

Included:

- The implemented OP01–OP10 schedules and separately audited OP10 `project_busy_watchdog`, indexed in the [Coverage Matrix](sqlite-ownership-closure-coverage.md). Every protected result remains **PASS WITH LIMITATION**. OP06's unsafe run remains **EXPECTED COUNTEREXAMPLE**, excluded from protected-protocol success.
- Ordinary Node on the recorded local Windows x64 environment: Node v24.21.0, modules 137, N-API 10, better-sqlite3 13.0.3, SQLite 3.53.4. This names the tested tuple, not every filesystem/VFS or future runtime.
- Synthetic PA/S1/G1 bindings in fresh Harness-owned temporary directories, actual separate SQLite Owner and Project files, actual independently spawned participants and fresh SQL Readers.
- Cooperative Writer processes using the recorded stable binding and private synchronous lifecycle. Owner and Project connections stay on one serialized execution thread; application-controlled release does not interleave between the final guard and COMMIT.
- Controlled observable rollback/close, normal release, actual owned process termination, fixture SQL failures, bounded contention and independent fixture history checks **at the scheduled boundaries**.

Excluded from any safety conclusion: genuine Driver/API release faults, OS/VFS release faults or hidden lock loss, successful live file replacement, independent physical Owner files for the same logical project, arbitrary SQL writers, all possible concurrency/crash instructions, real COMMIT I/O ambiguity, power loss, other platforms and production Host/Storage lifecycle. These exclusions describe this feasibility result; they do not amend accepted product scope or waive the existing production gates.

The relevant prerequisite is one stable physical Owner identity shared by participating writers and one valid Project generation. Copy/alias parameter rejection is not proof of enforcing that prerequisite against every filesystem/catalog race. If the actual product requires safety when that prerequisite fails, this architecture must address it before production; a narrow closure cannot grant that safety.

**Reasoned P1 disposition: retain real release failure as an explicit unverified boundary and recommend narrow closure.** The question being closed is the witnessed cooperative protocol under a stable binding, not native fault tolerance. All included positive/rejection/crash schedules have their own evidence; none relies on calling an actual unknown release successful. The controlled JS error paths support fail-closed intent but do not establish B/C. Not having a reliable OS fault injector is neither proof of safety nor a reason to append an uncontrolled destructive test to this review.

Conditional production reasoning, not an experimentally established native guarantee: stop intake before release; Project handles must drain/close before Owner release; an error leaves the old capability disabled and must not announce CLOSED, ACK or trustworthy recovery. Do not assume the Owner lock remains held after error. If another participant actually acquires the same valid Owner resource, it must recover/fence anew; no timeout/PID authority is used. If Project closure, ownership, identity or commit outcome cannot be established, return blocked/unavailable and preserve evidence, rather than replace/delete locks, revive the old candidate or reset state. This reasoning depends on actual lifetime and Driver semantics and therefore remains a production gate.

If the product's required support includes safe progress after an actual release fault or despite invisible/file-identity failure, those are **necessary production invariants**, not optional tests. Narrow closure does not waive them. They must be resolved by an explicit support/threat model decision plus evidence, or a reviewed architecture able to provide the required guarantee. If the final reviewers require those faults inside the _Spike closure scope itself_, this recommendation must instead become NOT READY FOR CLOSURE; do not silently expand the scope and preserve a passing label.
