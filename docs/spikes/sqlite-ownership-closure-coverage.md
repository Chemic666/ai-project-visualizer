## 4. P1: real release failure — fail-closed recommendation

`release_anomaly` successfully rolls back/closes Owner after a controlled pause. Rename/delete EBUSY is a filesystem mutation denial, not a release failure. Neither validates this branch.

Proposed contract, consistent with current JS Writer control flow:

1. Stop intake before release; rollback/close Project first. A Project closure error must not proceed to Owner release as if drain succeeded.
2. An error at Project close, Owner rollback or Owner close leaves the instance BLOCKED and permanently unable to write/publish/ACK. Do not announce CLOSED/released/success, renew a token, or reuse the old instance for business reconciliation.
3. On Owner release error, **do not infer whether the OS lock is still held**. Project is already closed before the Owner action; old business capability remains disabled. Another participant may proceed only after actual acquisition of the same stable Owner resource plus recovery and fresh epoch, never from time/PID or the error text.
4. If cleanup or lock identity cannot be established, preserve evidence and report blocked/unavailable. Do not delete/replace the Owner file, terminate normal user processes or pretend unknown release succeeded. Safe cleanup retries cannot revive intake; production retry/diagnostic policy still needs review.

Safe possible follow-up (not implemented/run here): a variant-scoped wrapper around a sacrificial connection's rollback/close can throw before the actual call, or after a known actual success, while exposing actual connection status. Test no publication, no early Owner release on Project failure, and B real-lock acquisition behavior with independent SQL. This is **Driver/API-boundary injection**, not an authentic driver malfunction or OS/VFS error. The current pure connection substitutes exercise JS branches only; no real SQLite load/process is involved.

There is no reviewed, reliable method here to force a genuine Windows SQLite unlock/close OS failure without uncontrolled behavior. File deletion/permission changes, native handle tampering and device faults may destroy assumptions and are not automatically authorized. Genuine OS/VFS release errors remain **NOT TESTED**, hidden loss **NOT GUARANTEED**. If such failures are mandatory within supported scope, component closure remains blocked until a safer separate experiment or architecture addresses them; tests cannot waive that requirement.

**Formal review recommendation:** real Driver/API and OS/VFS release failure may remain explicit NOT TESTED boundaries for a narrow cooperative fixture Spike. This is a limitation of the claimed scope, not evidence of real-fault safety. The known controlled schedules have complete evidence and no observed protected invariant violation; those conclusions do not depend on claiming such faults safe. The user has now authorized closure of that exact scope after reporting ChatGPT approval; native-fault safety is not approved. If production requires these faults to be safe, O01-g/M04 and lifecycle/error handling remain blockers; no gate is lowered. See the A–E distinctions and conditional safety reasoning in the formal review.
