# 第五步：定义 v0.1 End-to-End Acceptance Scenarios

## 1. 这一阶段的目标

前四步已经确定了：

```
产品是什么
↓
技术怎么选
↓
重大决策是什么
↓
用户界面怎么组织
```

第五步开始解决：

> **怎样才算 v0.1 真正做成了？**

不是：

```
Core 写完了
Adapter 写完了
UI 写完了
```

就算完成。

真正的标准应该是：

```
用户执行真实操作
↓
Codex 真实产生变化
↓
Visualizer 捕获变化
↓
Core 正确重建项目状态
↓
UI 正确展示
↓
用户能够理解并纠正
```

这才叫：

> **End-to-End。**

# 2. 为什么必须有端到端验收

如果没有 Acceptance Scenarios，很容易发生：

```
Core
✓

Storage
✓

Codex Adapter
✓

VS Code UI
✓
```

看起来全完成。

但真正运行：

```
Codex 修改 Plan
↓
Visualizer 没更新
```

或者：

```
Task 更新了
↓
Timeline 没有记录
```

或者：

```
Progress 变了
↓
用户不知道为什么
```

这种项目：

> 模块完成了，但产品没有完成。

所以 v0.1 必须以用户流程验收。

# 3. v0.1 的核心目标

v0.1 不是完整产品。

它只需要证明：

> **AI Project Visualizer 的核心产品循环成立。**

这个循环是：

```
Codex
  ↓
产生 / 修改 Plan
  ↓
Visualizer 捕获
  ↓
Project / Phase / Task 建立
  ↓
Progress 更新
  ↓
Timeline 保存变化
  ↓
用户可以查看和纠正
```

# 4. v0.1 核心能力范围

v0.1 只要求以下能力真正打通：

```
1. 自动识别项目

2. 自动识别 Codex Session

3. 自动捕获正式 Plan

4. 建立 Project / Phase / Task

5. 显示 Current Phase

6. 推断 Current Task

7. 显示 Confirmed Progress

8. 显示 Confidence / Provenance

9. 记录 Plan Change

10. 记录 Progress Change

11. Development Timeline

12. User Correction

13. Why X%?
```

以下内容**不是 v0.1 必须项**：

```
Semantic Analysis

Rolling Summary

Semantic Code Change

Verification Engine 完整版

多 Agent

多 Session 完整 UI

Cloud Sync

团队协作

Token / Cost
```

# 5. 验收规则

每一个 Scenario 都采用：

```
Given
前置条件

When
用户 / Agent 执行的动作

Then
必须发生的结果
```

必要时再加：

```
And
附加结果
```

这样以后可以直接转成：

- 手工验收；
- Integration Test；
- E2E Test；
- Codex 自检任务。

# Scenario 01 — 第一次打开项目

## 目标

验证 Visualizer 能够做到：

> **Zero-config first。**

## Given

用户已经安装：

```
AI Project Visualizer
```

用户打开一个正常项目：

```
my-project/
```

项目当前没有任何 Visualizer 配置文件。

## When

VS Code 打开该项目。

## Then

Visualizer 应：

```
自动识别当前 Workspace / Project
```

并能够打开：

```
Overview
Plan
Timeline
```

## And

不得要求用户首先：

```
project-visualizer init
```

不得强制创建：

```
.ai-project/
```

## Expected UI

如果 Codex 尚未运行：

```
Project detected

No active AI coding session.

Waiting for Codex...
```

# Scenario 02 — Codex Session 被识别

## 目标

验证 Codex Adapter 能够识别真实 Agent Session。

## Given

项目已经被 Visualizer 识别。

## When

用户在当前项目启动 Codex。

## Then

Visualizer 应识别：

```
Codex Session Active
```

并建立对应：

```
AgentSession
```

## Expected UI

顶部：

```
Codex ● Active
```

## Must Not

不得因为没有 Plan 就制造：

```
假的项目进度
假的 Current Task
```

# Scenario 03 — 自动捕获正式 Plan

## 目标

这是 v0.1 最关键的场景之一。

## Given

Codex Session 已经开始。

## When

Codex 生成正式开发计划：

```
Phase 1 · Foundation

- Setup project
- Create core model

Phase 2 · Storage

- Add persistence
- Add timeline storage
```

## Then

Visualizer 必须自动建立：

```
Project
├─ Phase 1
│  ├─ Setup project
│  └─ Create core model
│
└─ Phase 2
   ├─ Add persistence
   └─ Add timeline storage
```

## And

这些正式任务：

```
certainty = Confirmed
```

## Expected UI

Plan View 应能够显示：

```
○ Phase 1 · Foundation
  ○ Setup project
  ○ Create core model

○ Phase 2 · Storage
  ○ Add persistence
  ○ Add timeline storage
```

# Scenario 04 — Idea 不能自动成为正式 Task

## 目标

验证 Visualizer 不会把聊天里的每句话都变成计划。

## Given

正式 Plan 已经存在。

## When

Codex 在讨论中说：

```
以后也许可以支持云同步。
```

## Then

Visualizer 不应直接新增：

```
Confirmed Task:
Implement cloud sync
```

## Acceptable

可以：

```
Idea:
Cloud sync
```

或者暂时忽略。

## Must Not

这个 Idea 不得参与：

```
Confirmed Project Progress
```

Phase 1 所有 Confirmed Tasks 完成，并开始处理：

```

```


# Scenario 07 — 低 Confidence 必须暴露不确定性

## Given

当前 Codex 活动可能同时属于：

```
JWT Authorization
```

和：

```
Refresh Token
```

## When

Visualizer 无法高可信度区分。

## Then

UI 应显示：

```
Likely Current Task

JWT Authorization

Confidence
38%
```

并提供：

```
Correct
```

## Must Not

不能强行显示成：

```
Current Task
JWT Authorization
```

却不给用户任何不确定性提示。

# Scenario 08 — 用户纠正 Current Task

## Given

Visualizer 判断：

```
Likely Task
JWT Authorization

Confidence
55%
```

但用户知道真实任务是：

```
Refresh Token
```

## When

用户点击：

```
Correct
```

并选择：

```
Refresh Token
```

## Then

Visualizer 应更新：

```
Current Task
Refresh Token
```

## And

来源变成：

```
User Confirmed
```

## And

```
User corrected current task

JWT Authorization
→ Refresh Token
```

# Scenario 09 — Task Weight 初始估算

## Given

Plan 包含：

```
Update README

Implement Authentication

Implement Order System
```

## When

Visualizer 为 Confirmed Tasks 建立权重。

## Then

允许得到类似：

```
README              1
Authentication      8
Order System       12
```

## Must Not

所有任务默认永久使用：

```
weight = 1
```

作为最终正式进度模型。

# Scenario 10 — 用户修改 Task Weight

## Given

Visualizer 当前：

```
Authentication
Weight 8
```

用户认为实际复杂度更高。

## When

用户修改：

```
8 → 12
```

## Then

Task Weight 必须更新。

## And

Confirmed Progress 必须重新计算。

## And

Timeline 记录：

```
User corrected task weight

Authentication
8 → 12
```

## And

如果 Progress 变化：

```
64% → 59%
```

必须解释：

```
Reason:
Task weight corrected by user
```

# Scenario 11 — Confirmed Progress 正常增长

## Given

总 Confirmed Weight：

```
20
```

已经完成：

```
10
```

## Then

Confirmed Progress：

```
50%
```

## When

一个 Weight 4 的任务正式完成。

## Then

Confirmed Progress：

```
70%
```

## And

Overview 实时更新。

# Scenario 12 — Estimated Progress 与 Confirmed Progress 分离

## Given

Project：

```
Confirmed Progress
64%
```

当前正在处理一个大型任务：

```
Authentication
```

## When

Visualizer 判断该 Task 大约：

```
47%
```

## Then

UI 必须显示成两个独立数字：

```
Confirmed Project Progress
64%

Estimated Current Task
~47%
```

## Must Not

不能显示成：

```
Project Progress
67.2%
```

并把估算任务进度偷偷混入正式进度。

# Scenario 13 — Plan 扩张导致 Progress 倒退

## 目标

这是 v0.1 的核心差异化 Scenario。

## Given

当前：

```
Confirmed Progress
68%
```

Plan：

```
Authentication

✓ Login
▶ JWT
```

## When

Codex 正式扩展计划：

```
+ Refresh Token
+ Token Revocation
```

并将它们标记为 Confirmed。

## Then

总 Confirmed Weight 增加。

Confirmed Progress 可以变成：

```
64%
```

## And

UI 必须显示：

```
68% → 64%
```

## And

原因：

```
Plan expanded
```

## And

Timeline：

```
Plan changed

+ Refresh Token
+ Token Revocation
```

# Scenario 14 — Plan 变化不能覆盖历史

## Given

旧 Plan：

```
Authentication
├─ Login
└─ JWT
```

## When

新 Plan：

```
Authentication
├─ Login
├─ JWT
├─ Refresh Token
└─ Token Revocation
```

## Then

Visualizer 必须同时保留：

```
Previous Plan Snapshot
Current Plan Snapshot
Plan Diff
```

## Must Not

不能只保留最新 Plan，导致用户无法知道：

```
什么时候新增了任务
```

# Scenario 15 — Why X%?

## Given

Overview：

```
Confirmed Progress
64%
```

## When

用户点击：

```
Why 64%?
```

## Then

Visualizer 必须显示至少：

```
Completed Weight
Total Confirmed Weight
Completed Tasks
Remaining Tasks
Recent Progress-affecting Plan Changes
```

例如：

```
Completed
32

Total
50

32 / 50 = 64%
```

## And

如果之前是：

```
68%
```

还应显示：

```
68% → 64%

Reason:
Plan expanded
```

# Scenario 16 — Agent 报告 Task 完成


## When

```

```


# Scenario 17 — COMPLETED 与 VERIFIED 区分

## Given

Codex 已报告：

```

```

## Then

```

Reported by:
Codex

Verification:
Unknown
```

```

Tests passed
```

才允许：

```

```

# Scenario 22 — 多来源冲突的数据模型能够表达

v0.1 UI 不要求完整实现多源冲突处理。

但 Core 至少不能把未来路线堵死。

## Given

未来存在：

```
Codex:
Authentication = IN_PROGRESS

TODO.md:
Authentication = DONE
```

## Then

数据模型应该能够表达：

```
Source A state
Source B state
Unified state
Conflict flag
```

而不是只能保存一个：

```
status
```

并永远不知道它来自哪里。

# Scenario 30 — Magic Moment

这是 v0.1 最重要的人工验收场景。

## Given

用户在：

```
18:30
```

离开电脑。

当时：

```
Progress
68%

Current Task
JWT Authorization
```

Codex 持续工作。

期间：

```
JWT Authorization completed

Plan expanded:
+ Refresh Token
+ Token Revocation

Current Task changed:
Refresh Token

Progress:
68% → 64%
```

## When

用户：

```
18:40
```

回来并打开 Visualizer。

## Then

用户应在约 5 秒内理解：

```

64%

Phase
Authentication

Current Task
Refresh Token

JWT Authorization
Completed by Agent

Plan changed
+ Refresh Token
+ Token Revocation

68% → 64%
```


# 9. v0.1 Definition of Done

v0.1 不能用：

```
代码基本写完
```

作为完成定义。

必须满足：

## Product

```
P0 Acceptance Scenarios 全部通过
```

## Core

```
Project / Phase / Task
Progress
Timeline
Provenance
Correction
```

都有测试。

## Codex Adapter

真实 Codex Session 可以：

```
Plan
Session
Task Activity
```

进入 Normalized Events。

## Storage

重启后能够恢复项目状态。

## VS Code

Overview / Plan / Timeline 可正常使用。

## Trust

用户能区分：

```
Observed
Agent Reported
Visualizer Inferred
User Confirmed
```

## Privacy

默认核心功能不依赖云端源码上传。

# 10. 每个 Roadmap Phase 如何使用这些 Scenario

以后比如正在开发：

```
Phase 4 — Progress Engine
```

完成时不能只说：

```
Progress Engine implemented.
```

必须回头验证相关 Scenario：

```
Scenario 11
Confirmed Progress

Scenario 12
Confirmed vs Estimated

Scenario 13
Plan Expansion

Scenario 15
Why X%?
```

全部通过才能标：

```
Phase 4 complete
```

# 11. Work / Codex 的验收要求

以后 Agent 完成某个阶段时，要求它输出：

```
Implemented:
...

Tests:
...

Acceptance Scenarios verified:
- Scenario XX PASS
- Scenario XX PASS

Not yet supported:
...

Known limitations:
...
```

而不是只输出：

```
Done.
```

# 12. 自动化测试和人工验收的区别

并不是所有 Scenario 都一定能完全自动化。

例如：

## 适合自动化

```
Plan Diff

Progress Calculation

Progress Regression

User Correction

Persistence

Provenance
```

## 适合集成测试

```
Codex Event
→ Adapter
→ Core
```

## 需要人工 UX 验收

```
5 秒是否能理解

界面是否把 Estimated 和 Confirmed 混淆

Magic Moment 是否真的成立
```

所以最终需要：

```
Automated Tests
+
Human Acceptance
```

而不是只看测试数量。

| Scenario          | Core | Adapter | Storage | VS Code | Status  |
| ----------------- | ---- | ------- | ------- | ------- | ------- |
| Auto Plan Capture | ✓    | ✓       |         | ✓       | Pending |
| Progress          | ✓    |         | ✓       | ✓       | Pending |

> 为什么某个 Scenario 还没真正打通。

# 14. v0.1 不追求什么

v0.1 不追求：

```
功能最多

界面最漂亮

支持最多 Agent

支持企业协作

AI 分析最强

复杂数据可视化
```

只追求：

> **第一次把“AI 项目状态观察”这条完整链路做通。**

# 15. v0.1 最重要的成功问题

发布前只问：
