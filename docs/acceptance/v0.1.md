# 第五步：定义 v0.1 End-to-End Acceptance Scenarios

## 1. 这一阶段的目标

前四步已经确定了：

```
产品是什么
↓
技术怎么选
↓
重大决策是什么
↓
用户界面怎么组织
```

第五步开始解决：

> **怎样才算 v0.1 真正做成了？**

不是：

```
Core 写完了
Adapter 写完了
UI 写完了
```

就算完成。

真正的标准应该是：

```
用户执行真实操作
↓
Codex 真实产生变化
↓
Visualizer 捕获变化
↓
Core 正确重建项目状态
↓
UI 正确展示
↓
用户能够理解并纠正
```

这才叫：

> **End-to-End。**

# 2. 为什么必须有端到端验收

如果没有 Acceptance Scenarios，很容易发生：

```
Core
✓

Storage
✓

Codex Adapter
✓

VS Code UI
✓
```

看起来全完成。

但真正运行：

```
Codex 修改 Plan
↓
Visualizer 没更新
```

或者：

```
Task 更新了
↓
Timeline 没有记录
```

或者：

```
Progress 变了
↓
用户不知道为什么
```

这种项目：

> 模块完成了，但产品没有完成。

所以 v0.1 必须以用户流程验收。

# 3. v0.1 的核心目标

v0.1 不是完整产品。

它只需要证明：

> **AI Project Visualizer 的核心产品循环成立。**

这个循环是：

```
Codex
  ↓
产生 / 修改 Plan
  ↓
Visualizer 捕获
  ↓
Project / Phase / Task 建立
  ↓
Progress 更新
  ↓
Timeline 保存变化
  ↓
用户可以查看和纠正
```

# 4. v0.1 核心能力范围

v0.1 只要求以下能力真正打通：

```
1. 自动识别项目

2. 自动识别 Codex Session

3. 自动捕获正式 Plan

4. 建立 Project / Phase / Task

5. 显示 Current Phase

6. 推断 Current Task

7. 显示 Confirmed Progress

8. 显示 Confidence / Provenance

9. 记录 Plan Change

10. 记录 Progress Change

11. Development Timeline

12. User Correction

13. Why X%?
```

以下内容**不是 v0.1 必须项**：

```
Semantic Analysis

Rolling Summary

Semantic Code Change

Verification Engine 完整版

多 Agent

多 Session 完整 UI

Cloud Sync

团队协作

Token / Cost
```

# 5. 验收规则

每一个 Scenario 都采用：

```
Given
前置条件

When
用户 / Agent 执行的动作

Then
必须发生的结果
```

必要时再加：

```
And
附加结果
```

这样以后可以直接转成：

- 手工验收；
- Integration Test；
- E2E Test；
- Codex 自检任务。

# Scenario 08 — 用户纠正 Current Task

Given：Visualizer inferred JWT，confidence 55%，用户实际选择 Refresh Token。
When：用户纠正当前关联。
Then：当前结论为 Refresh Token / User Confirmed；保留原 assertion、correctionId、Project/Session scope、时间及 Timeline。JWT 的 Agent-reported status 来源不被改写。

## 必须验证的后续行为

- 普通文件 activity、新 Turn、时间流逝、重启后仍保留有效纠正，不被普通推断覆盖。
- 断连显示 last confirmed/stale；不视作 Session 结束。
- 同 Session 可可靠识别且较新的显式源任务选择，或明确 Session 结束、完整计划明确移除目标，才按 D-037 失效；记录原因/规则/时间/trigger event。
- 不能确定新旧时保留纠正并暴露冲突。重复事件不能重复失效或生成重复 Timeline。
- 历史 association correction 只影响指定 event/集合，由后续人工纠正替代；不改变未来活动默认关联。

# Scenario 09 — Task Weight 来源与初始化

Given：Confirmed Plan tasks 有明确来源权重，例如 README=1、Authentication=8、Order=12。
When：Core 接收这些来源 assertion。
Then：各权重保留独立来源、revision/时间和解释；用户可编辑，不需要开启 Semantic Analysis。

没有来源权重的默认算法在 Phase 4 前单独批准并验证（Technical Verification Pending）；无有效权重时说明 progress unavailable，不能只排除这些任务来显示百分比。不将永久全 1 或必开 LLM 作为静默替代。示例值不是已校准复杂度模型。

# Scenario 10 — 用户修改 Task Weight

独立权重纠正示例（非 Scenario 13 的计划扩张）；本例分母变化由人工调整引起。

Given：completed weight=32，total confirmed weight=50，未完成 Authentication weight=8。
When：用户改为 12。
Then：weight assertion 为 User Confirmed，保留原估计；total=54，32/54=59.3%，显示 64%→59.3%，原因 Task weight corrected by user，并追加纠正及进度 Timeline。

后续 Agent 新估计、普通推断、新 Turn 或重启不得覆盖人工权重。再次人工调整或任务明确退出当前计划才按 D-037 替代/结束；失效有历史，重新纳入计划不静默复活旧纠正。拒绝零/负/非有限权重。

# Scenario 11 — Confirmed Progress 有依据增长

独立完成增长示例（非 Scenario 13）；本例完成权重变化，分母不变。

Given：total confirmed weight=20，已有可靠完成依据的 weight=10，progress=50%。
When：weight=4 的正式任务获可明确归属的 Agent completion report。
Then：COMPLETED / Agent Reported，保留事件/修订依据，progress=14/20=70%；未自动 VERIFIED。

## 必须验证

- fixture 中独立验证依据支持的 VERIFIED 也可计入，但一项任务只计一次。
- 缺失可靠完成依据的 visualizer_inferred completed（即使 confidence 99%）不进入 completed weight；状态解释暴露缺失依据。
- 不把 Turn 结束、文件修改、通过一个命令或 Agent 总结中的测试描述直接升级为独立 VERIFIED。
- 重开任务移出分子；移除正式任务调整当前分母但保留历史；Phase weight 不第二次乘数。
- 无 Plan、零分母或任何正式任务权重无效/缺失，progress unavailable。精确值计算，UI 一位小数、去掉 .0。

Core fixture checks 在 Phase 4，真实观察/Overview 更新的 E2E 在 Phase 10/11，不能互相替代。

# Scenario 12 — 非混合约束与后续 Estimated 功能

## 12A — v0.1 P0：不混合，且不展示数值估算

独立非混合示例；64% 为既有正式进度，不演示 Scenario 13 的扩张过程。

Given：Confirmed Project Progress=64%，当前 task in_progress，association Confidence=65%。
When：收到更多文件活动、部分完成声明或更高关联 confidence。
Then：没有可靠完整完成依据时，不增加分子；分别展示 Confirmed Progress、Current Task、Current Task Confidence 和来源。v0.1 不计算/展示 Estimated Task Progress 数字，不显示占位 ~0%/~47%，也不把 confidence 当完成比例。

## 12B — Phase 13：双数字分离（非 v0.1 门槛）

独立后续展示示例（非 Scenario 13）；任务估算比例不参与正式进度计算。

未来经 Phase 13 实现和验证后，Confirmed=64%、Estimated Current Task≈47% 可以独立展示，并记录 estimate confidence/依据。估算不得混入正式进度，也不复用 association Confidence。当前 **Not implemented / Technical Verification Pending**，不在 Phase 4/v0.1 强制通过。

# Scenario 13 — Plan 扩张导致 Progress 倒退

Given：completed weight=32、total confirmed weight=45，UI=71.1%；JWT 仍 in_progress，Login 仅有 Agent 完成声明时使用 ◐。
When：完整正式计划新增 Refresh Token weight 3、Token Revocation weight 2，certainty=confirmed。
Then：分子仍32，分母50，UI=64%；显示 71.1% → 64%，reason=plan_expanded，关联 previous/current plan revision 和新增任务依据。Timeline 展示计划/进度变化；不能伪造新增理由，来源没有理由时显示未提供。

重复 plan revision 不重复新增权重或 Timeline。若只收到部分快照，不据此移除其他任务。

# Scenario 16 — Agent 报告 Task 完成

Given：明确 taskId/revision 的 JWT in_progress。
When：收到能可靠关联该任务的显式 completion report，而非无归属“done”或 Turn completion。
Then：COMPLETED / Agent Reported，保留来源事件及时间，可按 D-035 纳入 completed weight；verification unknown。不能自动 VERIFIED，也不能因 Activity association 被人工纠正而改写其完成来源。

没有可靠归属/依据的报告保留来源并说明不确定，不猜测为某任务的正式完成。

# Scenario 19 — Timeline 不被 Raw Activity 淹没

Given：受支持来源实际提供一组 read/edit/run activity。
Then：Timeline 不默认逐条复制 tool events；保留有项目意义且有依据的 task/plan/progress/correction 变化。Activity 为 advanced/P1，事件存在与否按 capability 表示。

只有获得实际 result 或明确 Agent 声明才能显示相应“Test failed”，并区分 Observed/Agent Reported；语义 continued fixing 如为推断须披露。此要求不引入 Phase 14 verification engine 或 semantic summary。Raw 私有输出不因归一化而默认保存。

# Scenario 30 — Magic Moment

独立示例（非 Scenario 13）：先完成任务，再扩张计划，因此保留两个进度变化及各自原因。

Given：18:30 离开时 completed weight=28、total=40，progress=70%，Current Task=JWT Authorization（weight4，in_progress）。
When：正常 Codex 工作流在受支持路径上提供：

1. 明确 JWT completion report：32/40=80%，COMPLETED / Agent Reported，verification unknown。
2. 正式新增 Refresh Token weight6、Token Revocation weight4：total50，32/50=64%。
3. 当前关联 Refresh Token，保留来源与适用 Confidence。

Then：18:40 回来后 Overview 在约5秒内让用户理解 Authentication / Refresh Token、JWT 完成声明、两项新增、70%→80%→64% 以及各自 completion/plan expansion 原因，无需 Chat/Terminal/Diff。

不要求 numeric task estimate、LLM rolling summary 或高级 Since Last Viewed。必须真实 Codex E2E + 人工理解验收；fixture/mockup 成功不能证明该场景已通过。当前 Pending。

# 9. v0.1 Definition of Done

- Product：全部 P0 + Mandatory Trust/Privacy Gates 通过；v0.1 无 numeric Task estimate。
- Core：Project/Phase/Task、来源/事件身份与幂等、权重/完成依据、解释、Timeline、纠正/失效范围均有必要 fixture checks。
- Adapter：D-038 被动观察门槛通过且支持范围获批准；真实 Session/Plan 更新/任务信号归一化，未知能力明确报告。
- Storage：driver/host packaging 验证通过；恢复保留 provenance、history、有效纠正/cursor，无重复派生事件。
- VS Code：Overview/Plan/Timeline、Task Detail/Correction、Weight 编辑、Why 和必要 Settings 可用；Empty/unknown/disconnected 基线完整。
- Acceptance：真实路径 E2E、重启/隐私检查和人工五秒理解分别有证据。Core fixture 不能冒充真实集成通过。

当前没有实现/技术验收结果；此文档定义要求，不代表已 PASS。
