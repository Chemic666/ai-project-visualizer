# Phase 2.3 — Production Support and Failure Contract

Date: 2026-10-09 (Asia/Shanghai). **Status: Proposed / architecture review required / no production implementation or enablement authorized.**
**Writer direction approval:** the user reports ChatGPT approval of B + C, retaining A. This revision converges normative Proposed constraints with [design §§4/6–8/12](phase-2.3-design.md); it does not accept D-041–D-044 or grant production support. Mandatory clauses are design obligations whose enforcement is still UNVERIFIED/NOT TESTED, not a runtime PASS.

The [Ownership Spike](../spikes/sqlite-ownership-closure-review.md) is **CLOSED — PASS WITH LIMITATION**, only for its narrow cooperative component scope. This document proposes the production admission conditions, failure semantics and verification gates that its closure does not supply. Phase 2 is incomplete; production single-Writer safety is not yet established. D-041–D-044 remain Proposed. better-sqlite3 13.0.3 remains the existing preferred proposal, not a newly accepted Driver decision.

Basis: [Phase 2.3 design](phase-2.3-design.md), [existing 25-case/O01/O02 acceptance](../acceptance/phase-2-storage.md), [immutable coverage/evidence index](../spikes/sqlite-ownership-closure-coverage.md), [archived compatibility results](../spikes/sqlite-driver-compatibility-results.md), and D-041–D-044 in [DECISIONS](../../DECISIONS.md). No other specification is amended. Requirements and support exclusions below are proposals for review, not claims that production currently supports them.

## 1. Support, guarantee and evidence labels

Use separate support/guarantee labels; the proposed initial candidate has **no currently SUPPORTED production tuple**:

| Label          | Normative interpretation in this Proposed contract                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SUPPORTED      | Exact deployment and failure scope approved, required then-current implementation/admission/Host gates passed. Direction approval or a disposable PASS is insufficient; none qualifies yet              |
| UNSUPPORTED    | Proposed forbidden deployment/path/operation: reject Writer admission when identified. It does not imply the condition cannot occur, or that an invisible fault is detectable                           |
| UNVERIFIED     | Candidate support, identity/API behavior or enforcement lacks required production evidence/approval; no business permission may be granted on the missing mandatory fact                                |
| NOT GUARANTEED | Strong safety property absent from the current mechanism/failure model, even if tests pass. Not a synonym for an untested implementation; requires scope decision or stronger architecture if mandatory |

An otherwise admitted Windows machine can still suffer hidden loss, replacement or I/O errors. Calling a deployment/failure unsupported cannot prove impossibility. The undetectable-loss/final-window scope gate remains C-class/P0 until a satisfactory bounded failure model is justified and approved; if it cannot be, production is blocked. Ordinary observable supported-environment API/I/O errors must still be handled fail-closed.

Evidence labels below remain distinct from those support labels:

| Label                   | Meaning in this draft                                                                                                    |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| SPIKE VERIFIED          | Direct evidence for the recorded disposable schedule/tuple only, with PASS WITH LIMITATION; not production approval      |
| PROPOSED FOR PRODUCTION | Candidate condition/behavior requiring explicit approval and its mapped verification before enablement                   |
| NOT TESTED              | Missing direct evidence for that exact production behavior, environment or failure; cannot infer PASS from another layer |

Verification and admission are separate dimensions. A SPIKE VERIFIED row may still have production status NOT TESTED. No runtime tuple is enabled by this document. Original OP10 and P0 top-level CMD exit codes remain **UNVERIFIED**, independently of their protocol audits; a later run cannot fill a historical exit code.

**Admission is fail-closed:** an unreadable or unproved mandatory environment/binding condition yields no Writer. ### 2.1. Normative Proposed identity and failure-model admission

One logical Project must resolve one authoritative per-user catalog/StoreKey, one stable Owner incarnation across generations and one active Project DB incarnation with **one WAL/SHM/journal namespace**. All supported windows/profiles must converge before business permission. Independently allocated ProjectId remains separate from paths, physical IDs and Agent/VS Code identities. A copied marker, canonical-path string, globally lowercased path or main-file identity alone must not grant equivalence. Unknown/ambiguous root or catalog conflict blocks acquisition/new binding; no fallback owner path or new ProjectId to bypass the conflict.

Host must check actual local volume/access/case semantics and resource identity using a reviewed metadata/open/lifetime method. APV private DB paths must not use unexpected Junction/Symlink/reparse routing, Hard Links or alternate database names. A project-root alias can reuse a binding only after its equivalence is established; otherwise reject that entry without changing user paths. Copies/worktrees/moves must not be merged by name/remote/content. Every connection opens the one admitted path and common sidecar domain. See [design §4.1](phase-2.3-design.md) for the bounded rules; Windows identity API integration and race-resistant metadata-to-Driver binding remain **UNVERIFIED, C-class/P0**, not an assumed implementation.

Proposed forbidden deployments are network/UNC/mapped-network or cloud-synced roots, removable/unsupported virtualized storage, remote/web/WSL/container Hosts and any unresolved namespace/access condition. The initial candidate is a reviewed fixed local NTFS Windows x64 tuple, not blanket NTFS support. Restart must revalidate root/catalog/incarnation/generation and acquire actual Owner before recovery/fencing. Missing active-bound files and unexpected move/rename/replace/recreate must revoke permission once detected and return unavailable; no automatic empty bootstrap. Authorized retirement/resume preserves stable Owner and closes data handles before managed generation replacement.

Hidden Owner loss can invalidate lifetime exclusion while same-Project transaction fencing still rejects post-new-epoch old capabilities. Hidden Project locking failure or split Project/sidecar identity invalidates that conditional fencing premise itself. Neither failure is made impossible by the medium restrictions. Successful file replacement and the final external Owner guard window remain NOT GUARANTEED; detecting some identity failures is mitigation only. Approval must specify acceptable dependency/failure assumptions and their limits; absent a satisfactory scope, keep the architectural blocker instead of enabling production.

## 3. Shared authority and fail-closed policy

These are design vocabularies, not new Core status types or a production state-machine implementation:

| Disposition           | Permitted behavior                                                                                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SAFE_CONTINUE         | Supported healthy binding; confirmed full cut; live current Owner/epoch/token for writes. Validate every candidate; do not infer health from an old acquisition                    |
| WAIT_OR_BOUNDED_RETRY | Known contention or proven not-committed outcome under healthy ownership; no new state publication/ACK while waiting. No force takeover                                            |
| WRITE_REVOKED         | Disable intake, queued candidates, write/publication/ACK capability. Attempt safe rollback/data closure while preserving evidence. The same failed instance cannot silently revive |
| UNAVAILABLE           | Authority, binding, outcome or recovery cannot be proved. Return no current reconstructed state; preserve originals, no empty defaults/rewind/Driver fallback                      |
| ENABLEMENT_PROHIBITED | Required safety depends on unapproved/unverifiable support assumptions or an unsupported environment. Do not enable production until the contract/gate or architecture changes     |

Only a confirmed healthy cut of the active generation may be represented as current. A separately validated older cut can be **last-known**, labeled with its generation/head and stale/unavailable recovery, capture/ACK paused; it is not successful current restoration. Do not relabel old snapshots, fabricate todo/zero/100%, expire corrections, upgrade Agent Reported to Verified, or replace confidence/provenance. A Writer health label is not a Task WorkStatus.

Mandatory invariants:

1. The catalog supplies one stable physical Owner binding across windows/generations. Owner acquisition is HELD_UNFENCED, not permission to ingest/write. Valid recovery and confirmed Project epoch/token persistence precede ACTIVE.
2. Every protected business write **successfully obtains Project BEGIN IMMEDIATE before** reading that transaction's current persisted Project/generation/lifecycle/epoch/token and authorizing the presented private capability. No transaction-external cache, old read snapshot, saved token or Owner flag is an authorization substitute. Compare expected base/references and guarded affected row count in that same transaction; mismatch must roll back every tentative effect, not COMMIT prior DML. The private live-Owner/lifecycle guard is a separate immediate pre-COMMIT check on the same serialized thread.
3. Observable loss or uncertain outcome disables writes. Project handles/candidates must be drained and proven unable to submit later work before Owner release. An Owner error does not prove either retention or release of the physical lock.
4. A confirmed Project COMMIT includes its whole applicable event/Assertion/source/correction/version/ledger/receipt/cursor bundle, and Snapshot/watermark if actually generated. No unsupported Engine output is invented. COMMIT precedes publication/consumption confirmation.
5. External source ACK is outside SQLite's transaction. After a commit-before-ACK crash, only a valid current ACTIVE owner may reconcile/re-ACK a proven covered unit. Receipt retry uses stable operation identity and intent excluding transient execution token, and publishes current head rather than an old receipt's historical state.
6. SourceId/sourceEventId, source cursor, local ledgerSequence and snapshotWatermark remain distinct. Cursor alone is not event identity; absent stable identity preserves declared at-least-once behavior, not fabricated exactly-once.
7. Fault diagnostics pass D-043 allowlists before persistence/output: safe category, approved opaque identity/phase and bounded metadata only. No raw SQL bindings, Error.message/stack, argv/env, secret paths, source/prompt/tool payload. Quota failure cannot drop input and then advance cursor/ACK.

Owner DB coordinates actual acquisition, contention, normal handoff and private lifetime; it is not business authority or the location of fencing epochs. Project DB contains durable fencing state, in-transaction capability guards, full atomic records/dedup/receipt/cursor authority. **No cross-file atomicity** exists. Valid admission → actual Owner HELD_UNFENCED → verified recovery → confirmed same-Project fencing → ACTIVE → each checked business transaction → confirmed outcome/current-lifecycle publication and covered ACK → revoke/drain/close Project → release Owner is mandatory. New creating/bootstrap and maintenance paths follow [design §6.3](phase-2.3-design.md), never an unguarded production DML exception.

| Safety claim                                                            | Converged Proposed boundary / evidence                                                                                                                                                                                                                                                                                    |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New epoch COMMIT excludes later old-capability business COMMIT          | Conditional on same physical Project/generation/sidecar domain, reliable write serialization, no authority reuse and all writes checked inside their acquired transaction. Old data first means fencing waits; fencing first means old mismatch rolls back. Conditional reasoning only; production enforcement NOT TESTED |
| One lifetime Writer / normal handoff                                    | Requires one actual Owner binding/exclusion, private capabilities and Project-before-Owner release. Same-DB serialization alone is not logical intake/publication exclusivity                                                                                                                                             |
| Observed Owner loss                                                     | Permanently revoke instance, cancel future work and roll back pending Project effects; actual API/error/lifecycle enforcement pending                                                                                                                                                                                     |
| Hidden loss / successful replacement / final external Guard–COMMIT race | NOT GUARANTEED. Old Project transaction can commit before B can fence even after Owner loss. If unconditional prevention is required within support, **ARCHITECTURAL BLOCKER**; no production support scope approved by this table                                                                                        |
| Unknown COMMIT / release error / recovery                               | No speculative publication/ACK or capability revival; settle suspect work and reconcile current authority on a fresh healthy connection. Actual native faults and full Host recovery NOT TESTED                                                                                                                           |

### Retry, watchdog and reacquisition bounds — Proposed

Retain the existing proposal's initial **250 ms SQLite busy_timeout** and at most **one** bounded retry for a proven-not-committed _business_ transaction with unchanged operation identity/intent/base and valid ownership. No retry on identity conflict, retired generation, uncertain outcome, corruption or loss. No blind COMMIT replay. Initial control/ownership contention observation budget: **5 s monotonic**, a Proposed tuning value requiring actual Host evidence, not a guaranteed product latency. Restoration/migration budgets need separately reviewed workload measurements; do not use five seconds to discard authoritative history.

**Converged Proposed rule:** there is no automatic fencing retry/activation of a failed acquisition instance. Initial fencing BUSY/error retires the candidate; only after safe data/Owner closure may a fresh acquisition proceed. Design §6 now specifies the same business-versus-control distinction. A data retry after verified rollback is a different case; timings and actual Host enforcement still require approval/evidence and no accepted Core behavior changes.

A JavaScript timer cannot prove cancellation of synchronous native SQL/I/O on its own thread. The P0 parent timer bounded an already BLOCKED Worker after a returned BUSY; it does not demonstrate production preemption of a hung call. A deadline never grants another Writer ownership. If a live call/handle cannot be proven finished, capture/ACK remains paused and no forced unlock or user-process termination occurs. A requirement for hard preemption needs its own reviewed isolation/lifetime design and evidence; none is implemented here.

Reacquisition always means actual same-resource Owner BEGIN under a valid catalog/binding, healthy recovery and a **fresh** epoch/token. PID, creation time, heartbeat, wall-clock age, timer expiry, a missing process-list entry or a failed close call never grants permission. No fallback lock path or window-specific catalog is allowed.

## 4. Failure Contract

For each F item, detection reliability refers to the listed observable signal. It is not a promise to detect hidden OS/VFS failure. All production cases/gates are **NOT TESTED** unless explicitly identified as component evidence. Each rule is Proposed.

### F01 — Owner acquisition failure

- **Trigger / signal / detection:** same bound Owner is held, unreadable, missing, marker/identity/schema invalid; real BEGIN returns BUSY, access error or binding rejection. BUSY rejection is observable; absence of a PID is not an ownership signal. The underlying lock's truth through invisible failure is not reliably detected.
- **Writer action:** no ACTIVE or Project write access; conflict/read-only on ordinary BUSY, unavailable on damaged/unproved binding. Never recreate an existing-bound Owner.
- **Automatic retry / reacquisition:** no acquisition retry loop. A later explicit bounded attempt is permitted on the same validated resource; actual lock acquisition/recovery/fresh fencing are required.
- **Publication / ACK / invariant:** no failed-candidate publication or ACK; one binding, no epoch/domain/cursor advance. A healthy independently validated read cut may be shown with truthful availability.
- **Evidence / production acceptance:** OP02/original OP10 same-lock refusal evidenced; production catalog/admission missing. O01-a/e/f, P03, M01/M04 must verify these outcomes and first-open race.

### F02 — Real Owner release/close failure

- **Trigger / signal / detection:** Project drain/close or Owner rollback/close throws, returns an uncertain result or cannot be confirmed. API error is observable; whether the physical Owner lock survived is **not** reliably established by that error/open flag.
- **Writer action:** revoke writes/intake/publication/ACK before cleanup. Close/settle Project first; if inability to submit a later Project commit is unproved, do not intentionally release Owner. Keep blocked/unavailable, preserve evidence and expose sanitized release outcome unknown. Never announce successful release merely because cleanup was attempted.
- **Automatic retry / reacquisition:** no automatic revival. Only reviewed idempotent cleanup attempts may occur after write revocation; they cannot perform business SQL. Fresh acquisition is allowed only after the old Project path is proven unable to commit, stable identity is verified, and another candidate actually acquires Owner. If those facts are unavailable, remain blocked; no PID/timeout takeover.
- **Publication / ACK / invariant:** none from the failed instance. Project-before-Owner lifetime and old-capability invalidation are mandatory; no assumption that the lock is retained. A new healthy ACTIVE owner alone can reconcile old committed work.
- **Evidence / production acceptance:** only pure JS substitutes exercise failures; real Driver/API and OS/VFS release errors **NOT TESTED**. O01-b/g/h and M04 need real connections plus precisely labeled before-call/after-call API injection and independent acquisition/SQL checks when authorized. Genuine OS error coverage remains separately labeled; unsafe filesystem destruction is not required by this draft.

### F03 — Hidden Owner lock loss

- **Trigger / signal / detection:** underlying lock disappears or coordinates incorrectly while Driver still reports open/inTransaction; there may be **no reliable signal**. A later BUSY/identity anomaly is not proof of when hidden loss occurred.
- **Writer action:** on any observed discrepancy, revoke writes and attempt Project rollback, then unavailable. For truly invisible loss this mechanism cannot promise timely fail-closed action; it must not claim detection it lacks.
- **Automatic retry / reacquisition:** prohibited from suspicion/time alone. No recovery until identity/lifetime/support conditions are independently established; unstable/known-broken lock environments must not be enabled.
- **Publication / ACK / invariant:** no publication after detected loss; an unconditional no-post-hidden-loss-COMMIT guarantee is **NOT GUARANTEED** by this design.
- **Evidence / production acceptance:** controlled loss in OP06/08 does not validate hidden loss. Before production implementation, approve a precise dependency/failure exclusion or a stronger reviewed ownership mechanism. O01-d/h, O02 and M04 need supported-environment evidence; no finite fault suite alone proves all invisible failures.
  Same-Project post-fence rejection may still hold if Project identity/serialization remain intact; it does not prove timely Owner-loss revocation or publication exclusivity. A plausible, explicitly reviewed failure boundary is still missing; §7 keeps this C-class blocker. An exclusion label alone cannot resolve it.

### F04 — Owner or Project resource replaced, deleted or renamed

- **Trigger / signal / detection:** opened Owner/Project or journal namespace differs from catalog/incarnation, its path vanishes, or root is recreated. Visible mismatch is detectable at inspected boundaries; successful replacement **between** inspection and use may not be detected in time. Equal main-file metadata cannot prove a shared WAL/SHM domain.
- **Writer action:** disable acquisition/active writes on mismatch; rollback/close data safely, preserve originals and return unavailable. Do not normalize to the replacement, create-as-repair or delete a live lock.
- **Automatic retry / reacquisition:** no automatic retry. Only explicitly resolved catalog/generation/resource identity with no stale writable participants permits a new actual acquisition. Normal generation deletion retains the stable Owner marker/resource.
- **Publication / ACK / invariant:** once detected, revoke future effects/ACK and settle data safely; no retroactive removal of an already committed fact. Split Owners defeat lifetime coordination; split Projects/sidecars invalidate the same-Project fencing argument. Safety under successful external replacement is NOT GUARANTEED, not repaired by a new nonce on another file.
- **Evidence / production acceptance:** OP09 Windows rename/delete denied EBUSY; successful replacement/directory recreation **NOT TESTED**, safety **NOT GUARANTEED**. O01-f/g, P03/P07/P08 and M04 require approved access/identity/maintenance boundaries and targeted supplements, not reuse of mutation denial as success-after-replacement evidence.

### F05 — Different physical Owner files for the same logical Project

- **Trigger / signal / detection:** competing initialization, independent profile catalogs, ambiguous root alias/move, copied Owner marker or divergent StoreKeys create two exclusion domains. Catalog/version/identity disagreement can be rejected; two isolated catalogs may not see each other without one authoritative binding design.
- **Writer action:** reject ambiguity and disable production admission; one short catalog binding transaction must select a stable StoreKey before either Owner opens. Never merge by name or filesystem path alone and never manufacture a new Project identity to evade the conflict.
- **Automatic retry / reacquisition:** only after binding conflict is resolved through reviewed catalog semantics. No path fallback or per-window fresh file.
- **Publication / ACK / invariant:** no effects from an ambiguous ownership domain; per-file exclusion is insufficient for logical single Writer.
- **Evidence / production acceptance:** OP09 alias/copy only reject parameters; actual divergent-resource contention **NOT TESTED**. Production implementation is blocked on binding contract; O01-a/f, P02/P03/P08 need concurrent first binding/profile/alias-generation checks with independent resources and a unified oracle.

### F06 — Project DB persistently BUSY

- **Trigger / signal / detection:** valid Owner exists but another connection holds required Project write resource; Project BEGIN/statement/COMMIT returns BUSY. Record the phase and actual transaction/outcome state separately; a generic timeout cannot classify COMMIT.
- **Writer action:** no activation before fencing. For pre-COMMIT data contention, verify rollback/not-committed and pause/recompute a new candidate as permitted; exhaustion revokes intake and enters blocked. A native hung call that cannot return is not declared canceled by a timer.
- **Automatic retry / reacquisition:** one bounded data retry only under §3's proven conditions; no fencing revival, lease expiry or Project lock destruction. Fresh ownership may resume only after data closure and real Owner reacquisition; if an obstacle remains, fail again without effects.
- **Publication / ACK / invariant:** no failed/uncommitted state or covered cursor/ACK advance. Re-ACK of an older committed unit requires a separate healthy current-owner reconciliation.
- **Evidence / production acceptance:** P0 directly proves returned fencing BUSY, blocked residence, real parent timer, cleanup and fresh commit; not a five-second SQL call or production scheduler. S02/S13, O01-e/h and M04 must cover actual Host retry/deadline/error paths and distinguish BEGIN BUSY from COMMIT uncertainty. Hard preemption remains unproved.

### F07 — Fencing persistence failure

- **Trigger / signal / detection:** epoch-control BEGIN/conditional update/COMMIT fails, Owner guard fails, generation/row count is invalid, epoch exhausts, or outcome is uncertain. Returned errors are observable; real uncertain COMMIT cannot be classified from a catch alone.
- **Writer action:** never ACTIVE; retire candidate and settle/rollback the Project transaction safely. Known complete rollback preserves old control cut. Unknown control outcome stays unavailable/blocked until F11 reconciliation; no cached token grants writes.
- **Automatic retry / reacquisition:** no automatic old-instance fencing retry. Fresh acquisition only after safe old data/Owner closure, verified current generation and complete cut; increments from the persisted epoch, not a guessed pre-error value. No epoch wrap/reuse.
- **Publication / ACK / invariant:** no control-only domain progress/ledger/cursor advancement or ACK; epoch/token COMMIT confirmation precedes ACTIVE.
- **Evidence / production acceptance:** OP08 scheduled failures and P0 BUSY evidenced; actual I/O uncertainty/nonce reconciliation **NOT TESTED**. O01-c/d, S02/S05, M01/M04 must verify rollback, unknown and exhaustion subcases with independent control reads.

### F08 — Epoch/token/generation/base mismatch

- **Trigger / signal / detection:** trusted catalog or current Project row does not match the candidate's Project/generation/epoch/token/expected head, or immutable operation ID has a conflicting intent. Reliably reject against readable validated authority; unreadable authority is F12, not a match.
- **Writer action:** after actual Project write-transaction acquisition, compare its current persisted control row; reject and fully roll back mismatched candidates, including earlier tentative DML/dedup/cursor effects. No overwriting old receipts, references, corrections or head; no outside-cache authorization or adopting the new token. Revoke stale capability; a normal data revision conflict may reload a validated base to form a distinctly reviewed new candidate.
- **Automatic retry / reacquisition:** no retry of stale capability or conflicting ID. A receipt match is reconciled before original base comparison, using stable intent independent from transient execution token. Reacquisition requires healthy binding/actual Owner/new token, never token reuse.
- **Publication / ACK / invariant:** rejected mutation has no effects. Identical proven committed operation may be reconciled/re-ACKed by a healthy current ACTIVE owner; publish current head, not its historical receipt's state.
- **Evidence / production acceptance:** OP05/07 and reinforced OP04 fixture checks support subsets. S05–S09/S13, P02/P08 and O01-b/g must prove real identity/dedup/cursor semantics and no cross-generation/project leakage.

### F09 — Final Owner guard–COMMIT external race

- **Trigger / signal / detection:** resource/lock changes after a successful final guard but before/during Project COMMIT. Private same-thread application release is preventable; arbitrary external loss is not reliably detected by this guard.
- **Writer action:** forbid reentrancy/shared native handles/await in the final section; detected pre-COMMIT loss rolls back. There is **no implementable guaranteed action for an invisible race** in this protocol. Do not claim later fencing can undo a prior old-epoch COMMIT.
- **Automatic retry / reacquisition:** no automatic repair of an unprovable invariant breach. Stop capture/ACK and preserve authority on an observed breach; require reviewed diagnosis/architecture, not a fresh token as a retroactive cure.
- **Publication / ACK / invariant:** guarded application schedules may publish only confirmed commits under valid current lifecycle; unconditional cross-resource guard/COMMIT atomicity is **NOT GUARANTEED**.
- **Evidence / production acceptance:** OP06 unsafe counterexample and protected controlled-loss schedules establish the gap/mitigation boundary. Before production implementation, approve the supported external-failure exclusion or review a coordination architecture with the stronger required property. O01-d/h/S13 do not prove hidden/external atomicity through finite timing tests.
  The unresolved external gap is Owner-state change, not a newer Project epoch concurrently committing through a healthy Project write lock held by A. B's fencing must wait for A's transaction; therefore S2 can hold while S3/S4 fail. Hidden Project VFS loss or different Project resources voids this conditional argument. Strong instantaneous revocation remains ARCHITECTURAL BLOCKER if required; reasonable residual-scope acceptance is not yet established.

### F10 — Process crash and restart

- **Trigger / signal / detection:** participating process exits or crashes before/after control/data COMMIT or source ACK; exit evidence is useful but is not ownership authority. Actual Owner acquisition plus readable recovery determines takeover, not process-list absence.
- **Writer action:** new process resolves the same binding/generation, acquires Owner, lets SQLite recover, then verifies the complete APV cut and allocates fresh epoch/token. Never open/create an empty active-bound store as successful recovery.
- **Automatic retry / reacquisition:** supervised fresh acquisition may occur after real resource acquisition; bounded BUSY still pauses. Retry prior operation only through proven receipt/body/cursor coverage. Unsupported/missing/mixed state is unavailable, not repeated bootstrap.
- **Publication / ACK / invariant:** old complete cut before COMMIT or new complete cut after COMMIT, no partial blend. ACK a verified covered unit only after current-owner recovery. Process crash is not power-loss verification.
- **Evidence / production acceptance:** OP04/08 fixture crash schedules evidenced; real full recovery **NOT TESTED**. S01/S03–S05/S10–S12, M02/M03, O01-c/O02 and P07/P08 need exact provenance/correction/acceptedEvents/generation and actual Host restart evidence.

### F11 — COMMIT result uncertain

- **Trigger / signal / detection:** COMMIT I/O/connection error, result loss or ambiguous close makes data/control persistence uncertain. Observe error/phase/candidate intent/control nonce; **cannot reliably detect committed/not-committed from return/throw, inTransaction or missing ACK alone**.
- **Writer action:** revoke writes/publication/ACK. Settle or safely close the suspect Project transaction so it is proven unable to commit later; retain valid Owner where possible. If that cannot be established, keep blocked/unavailable and do not intentionally release Owner. Under valid binding/ownership, inspect a **fresh healthy Project connection's consistent authoritative cut**: same resource/generation, receipt operationId/stable intent, canonical event identity, complete coverage and control nonce. An absent receipt **before** old-transaction settlement is not proof of rollback.
- **Automatic retry / reacquisition:** no blind replay. Match operationId plus stable intent/ref coverage, or current committed control token/nonce and expected generation/epoch, against fully validated authority. Matching receipt proves committed; absence proves not committed only after old writer/transaction cannot later commit and the healthy complete cut is established. A missing/superseded control nonce alone does not prove an earlier fencing COMMIT failed; preserve unknown attribution without adding a fictitious control history. If Owner was lost, retire old instance; only safe fresh acquisition/recovery/new fencing may authorize business retry. An inability to close is not time-based takeover permission.
- **Publication / ACK / invariant:** none while uncertain. Outcome inspection alone does not revive a BLOCKED candidate. A healthy current ACTIVE owner may publish current head/re-ACK a proven covered unit after reconciliation. Preserve old receipt/token history; execute no second canonical effect on matching stable identity. No global exactly-once claim for sources without stable identity.
- **Evidence / production acceptance:** OP04 post tests commit-before-ACK; OP08 `unknown` simulates uncertainty after known success. Actual COMMIT I/O uncertainty and true nonce/receipt reconciliation **NOT TESTED**. S04/S05/S12, M04, O01-c/d and P05 need safe independently labeled I/O/API failure subcases and settlement-before-absence checks; identity mismatch must not become success.

**2026-10-11 dated evidence/feasibility update:** the [Recovery Spike](../spikes/sqlite-recovery-closure-review.md) is formally CLOSED — PASS WITH LIMITATION for its independently audited U1/U2/U4/R1/R2/R3 fixture scope. The earlier evidence statement is retained history; U2 remains known-success response loss. The bounded [U3 Feasibility Review](phase-2.3-u3-feasibility-review.md) concludes **FEASIBLE WITH LIMITATION** for a conditional controlled VFS COMMIT-I/O error path, with native integration UNVERIFIED and **U3 NOT TESTED**. It does not prove a real Windows storage failure or authorize a build/run. F11 settlement/full-cut rules, B5/B6 blockers, Proposed Decisions and production acceptance remain unchanged.

### F12 — Database corrupt, missing or unreadable

- **Trigger / signal / detection:** CORRUPT/NOTADB/IOERR/access error, missing active-bound DB, unsupported marker/schema/codec/producer, ledger gaps or missing provenance/correction authority. Available errors/reference checks detect some faults, not every silent corruption; digests detect consistency errors, not malicious same-user modification.
- **Writer action:** revoke writes, current recovery unavailable, preserve all original DB/sidecars/backups and sanitized reason. Do not delete corrupt authority, downgrade, auto-switch Driver or initialize empty state. Normal SQLite interrupted-transaction recovery is acceptable only with verified all-old/all-new APV authority.
- **Automatic retry / reacquisition:** no blind write retry. A reviewed transient read check may be attempted without changing authority, but failure does not authorize another epoch or repair. Explicit backup recovery/migration may occur only under its separate reviewed policy/ownership; older backup is not latest-state proof.
- **Publication / ACK / invariant:** no current recovery/consumption ACK from unreadable authority. Explicit last-known is allowed only if independently validated, truthful about age/generation and compatible with current deletion/isolation policy.
- **Evidence / production acceptance:** full corruption/reference/migration coverage **NOT TESTED**. S12/M01–M04 and P02/P07/P08 must prevent fabricated state, mixed formats, hidden deletion and foreign-project recovery.

### F13 — Snapshot/watermark/cursor recovery inconsistent

- **Trigger / signal / detection:** snapshot body/vector/watermark not matching valid authoritative head, unsupported cache version, missing ledger tail, authoritative cursor ahead of covered events or wrong namespace/generation. Detect through one consistent cut, format/reference/digest and coverage checks, not array lengths or path names alone.
- **Writer action:** reject bad cache; under valid Owner reconstruct it only from independently complete supported authority at H with exact acceptedEvents and original provenance/corrections. Unknown authority, ledger gap or authoritative cursor inconsistency => unavailable. Never relabel the old cache or rewind cursor to make it fit.
- **Automatic retry / reacquisition:** cache-only rebuild/lossless approved migration may be automatic once authority is proven; source replay may not replace missing authority with fresh inference. Persistent repair requires actual Owner, confirmed current capability and a guarded Project write transaction (§6.3 of the design); pre-fencing recovery verifies read-only authority and does not write a cache. A Reader cannot mutate caches/cursors. Binding/lifecycle errors stop reacquisition.
- **Publication / ACK / invariant:** publish H only after full replay/reference/vector validation; no new facts or silent correction expiry. No source ACK until committed coverage is established; absent/unavailable conclusions stay unavailable.
- **Evidence / production acceptance:** Ownership fixtures do not contain this bundle; **NOT TESTED**. S08–S12/S01, P06/P08 and M01–M03 cover cache-only repair versus authority failure, codecs and retained history.

Quota/SQLITE_FULL, migration and deletion obey these same dispositions: reject the whole bundle or reconcile its uncertain outcome, never advance cursor/ACK after dropped input. D-044 numerical limits/backup TTL remain Proposed and unchanged; this draft does not introduce new retention values or authoritative history compression. P05–P08/M02–M04 remain required.
