# First Storage vertical slice — implementation and evidence

Date: 2026-10-19. **Implemented and tested on isolated synthetic data; production admission disabled.** This is an adapter implementation record, not a new Spike or full acceptance report. Policies D-041/D-043 are Accepted, D-042 Accepted — conditional architecture, D-044 Accepted — initial implementation policy; policy approval does not pass production gates.

## Delivered boundary

[`packages/storage`](../../packages/storage/README.md) adds an ESM implementation with `.d.mts` Core-compatible interface declarations. Implementation syntax/lint, declared API typechecking and runtime tests are separate checks. Core remains unchanged. The concrete Driver is injected only into the explicit development composition; no ORM, new Engine, fault extension, Agent or Host UI is introduced.

- Default `openProductionStore()` is permanently unavailable with `physical_binding_unverified`. Supplying `enabled:true` cannot enable it. No background collection or real-project path admission exists.
- The separate synthetic capability accepts only a fresh, empty, owned Windows TEMP child; actual fixed/local NTFS, ancestor reparse, realpath, dev/ino and hard-link checks are performed. Reopen binds the original nonce and directory identities. This is **not actual Driver-handle attestation** and does not solve metadata-to-open TOCTOU, ACL trust or B1.
- One private catalog binds Project/root to a random StoreKey/generation with creating/active states. Active stores cannot be silently recreated. The stable Owner DB holds a lifetime IMMEDIATE transaction; the same synchronous store owns its Project connection. Project uses WAL/FULL, foreign keys and no automatic WAL checkpoint. Each business transaction checks generation/epoch/token/base, records complete authority, receipt, optional Snapshot and covered checkpoint atomically. Project closes before Owner release; uncertain settlement retires/quarantines capabilities.
- Nine existing-design tables contain current Core data only: store_meta, commits, normalized_events, entity_versions, assertions, correction_versions, conclusion_versions, snapshots, source_checkpoint_versions. Normalized immutable events provide internal/stable-source Dedup; entity/correction/conclusion versions preserve History. Snapshot is a checked cache; full acceptedEvents are rehydrated from authority. Ledger sequence, Snapshot watermark, source identity and Cursor remain distinct.
- Strict recursive closed fields, limits and graph validation precede writes; errors expose fixed categories only. Matching source claims reuse the canonical input; mismatches reject. Optional missing identity and shared Cursor batches remain legal; no missing-identity stable dedup algorithm is invented. `synthetic.v1` is a test consumption codec, not proof of a real source's ordering/completeness.
- Matching operation/nonce/intent returns the original receipt without reapplying; original receipt epoch is historical, current ownership is checked separately. Normal COMMIT produces a receipt. Unknown COMMIT does not return guessed success/rollback or blindly retry; the instance becomes unavailable. No ACK, automatic publish or replay is implemented.

### Implemented interfaces and evidence levels

- [`openHost()`](../../packages/storage/src/host.mjs) remains **unavailable** for real projects, without creating a process/database. [`launchSyntheticHost()`](../../packages/storage/src/host-development.d.mts) is a separate explicit development composition. It requires an existing synthetic capability, exact installed Driver/native hash and a hash-bound actual Core module built under the disposable test root.
- Parent validates closed fields before IPC, accepts at most one in-flight operation and immediately rejects intake after close/revocation. One child privately owns **both** Owner and Project connections on one serialized thread. There is no lock-helper process, PID lease, automatic reconnect/retry, replay, publish or ACK. Diagnostic frames retain only allowlisted identity/header/status data; raw errors/stdout/stderr are not forwarded.
- [`inspectConnection()`](../../packages/storage/src/connection-binding.mjs) queries **the actual open Driver connection** through `PRAGMA database_list` and checks its `name`, the admitted main pathname and absence of foreign attached databases. SQLite's legitimate empty-file in-memory `temp` schema is permitted only with `temp_store=MEMORY`. This is connection-reported **pathname evidence**, distinct from filesystem dev/ino/reparse/hard-link checks. Neither attests the Windows file identity of SQLite's actual VFS-owned handle. No approved public JS method providing that bridge was found in current installed wrappers/native exports and the [v13.0.3 API](https://github.com/WiseLibs/better-sqlite3/blob/v13.0.3/docs/api.md). No new native API/extension/framework is introduced. **B1 remains open; actualDriverHandleIdentity is explicitly unavailable.**
- Active connections recheck reported paths and the admitted metadata. Observed WAL/SHM names stay within the Project sidecar namespace; once observed, inode disappearance/change while the connection remains open revokes the instance. This does not prove the actual SQLite-open WAL/SHM file IDs or eliminate external races.
- Fresh catalog initialization is exclusively created, with a small `catalog-admission.json` readiness proof created only after schema COMMIT. Competitors seeing incomplete admission stop before opening that catalog; existing bindings still converge through the catalog transaction and one StoreKey. `creating` remains unavailable. A missing/mismatching proof never creates another authority. This is development admission-format v1: older disposable roots lacking that proof are rejected unchanged, not silently migrated or reinitialized. Installation/profile-wide catalog convergence, private ACL trust and native resource binding are not thereby solved.

### Lifecycle and settlement

[`WriterLifecycle`](../../packages/storage/src/lifecycle.mjs) controls:

`ADMITTED → OWNER_HELD_UNFENCED → RECOVERED → FENCED → ACTIVE → REVOKING → DRAINED → CLOSED`.

Successful startup stages derive from actual Owner-acquisition, complete authority restoration and fencing-COMMIT receipts. Revocation may abort startup directly into REVOKING. Parent close disables intake synchronously; the already accepted operation completes or fails, then the child drains, closes Project and releases Owner last. `CLOSED` is emitted only after actual owned-child exit, IPC disconnect and stdio closure; Windows may deliver the exit event before the last IPC receipts, so the parent retains both and waits for drainage. RPC/Worker sequences, PID and a fresh per-child nonce are checked and retained. PID is diagnostic/channel binding, never lock authority.

Closure confirms the old process cannot submit later work, **not** a durable business outcome. Error/identity/unknown-COMMIT paths stay unavailable. Even a phase CLOSED with an expected rejection exit does not relabel the operation committed/not_committed. Real native release failures, hung native I/O, partial persistence and genuine COMMIT uncertainty are not verified. Unknown outcomes are never reconciled by receipt absence alone.

Requests are bounded to 8 MiB; complete-state responses have a separate 256 MiB envelope budget covering the accepted 128 MiB authoritative history and domain/transport overhead. Snapshot's 8 MiB cap excludes acceptedEvents and cannot serve as a full-state response cap. An independent review caught that defect; an actual >8 MiB event-ledger regression failed before the fix and passed afterward. These are implementation bounds, not measured production capacity claims.
