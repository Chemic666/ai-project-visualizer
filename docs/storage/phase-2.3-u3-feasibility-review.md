# Phase 2.3 — U3 COMMIT I/O Feasibility Gate

Date: 2026-10-11 (Asia/Shanghai). **Verdict: FEASIBLE WITH LIMITATION. U3: NOT TESTED. Native integration: UNVERIFIED.**

This is a bounded source/document feasibility judgment: a credible controlled VFS route can make the actual SQLite COMMIT encounter an I/O failure below the Driver. No injector exists or is qualified by this review. This is not an execution-ready gate, proof of a genuine Windows device failure, or a resolution of all uncertain outcomes. No build, DLL load, Driver load, database open, fault injection or experiment was performed. Stop this research here; implementation/execution requires separate approval.

Basis: [Support/Failure F11 and B5/B6](phase-2.3-support-and-failure-contract.md), [Storage design §8](phase-2.3-design.md#8-restart-incomplete-writes-and-ambiguous-commit), [Recovery README §3](../../experiments/phase-2-sqlite-recovery-spike/README.md#3-u3-real-commit-io-uncertainty--required-evidence-no-execution), [formal Recovery closure](../spikes/sqlite-recovery-closure-review.md), its unchanged [independent audit](../spikes/sqlite-recovery-evidence-audit.md), and [Acceptance](../acceptance/phase-2-storage.md). ## 1. Fault models and evidence boundary

| Model                                                     | Distinct recovery obligation / existing evidence                                                                                                                                                                                                                                                                               |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A: definite failure before successful COMMIT              | Establish actual rollback/termination and the complete old cut. A SQL exception alone is insufficient. U1's constraint failure and R1's controlled process termination cover their stated schedules only.                                                                                                                      |
| B: successful COMMIT, caller response lost                | Reconcile the complete committed cut and original intent/receipt before publication/ACK; avoid a second canonical effect. U2 covers this controlled simulation, not C.                                                                                                                                                         |
| C: actual I/O error during SQLite COMMIT                  | Prove a write/sync fault is inside the real COMMIT invocation, preserve the native extended result and transaction state, then settle and inspect fresh authority. Controlled VFS failures exercise this SQLite error path; actual Windows/hardware failures remain a separate untested category. U3 has no executed evidence. |
| D: COMMIT reports error, transaction may remain active    | Transaction activity is a separate axis within C and other failures. Never assume rollback; record activity before cleanup and its actual outcome. BUSY is not IOERR.                                                                                                                                                          |
| E: connection/process ends, final persistence unconfirmed | Exit can prevent later work from that process; it cannot prove which complete cut survived. Validate identity and fresh authority, or return unavailable. R2 covers known prior success, not general C/E uncertainty.                                                                                                          |

These paths cannot share a blind retry rule. SQLite documents possible statement-only or whole-transaction rollback on IOERR and other errors; a BUSY COMMIT can leave its transaction active. [Transaction error semantics](https://www.sqlite.org/lang_transaction.html). Autocommit state identifies transaction activity, not committed business outcome. [get_autocommit](https://www.sqlite.org/c3ref/get_autocommit.html).

Closed Recovery evidence remains six limited protocols, 1,640 matched inventory entries, 575 receipts, 162 commands, 70 Workers (68 normal, two controlled Windows terminations), 28 complete SQL cuts and two expected NOTADB errors. No historical database was reopened here. U4's six faults/unsettled case and R3's five faults retain their original refusal findings and individual references in the closure. L1–L7 remain intact. Missing identity, multi-event Cursor and positive generation paths remain Partial Coverage.

## 4. Recommended minimum, only after separate approval

First qualify candidate 1's exact binary/extension attachment and non-failing forwarding; if that fails, stop for review rather than silently switching builds. Then prepare only a stable-identity PA/G1 business bundle with its existing complete-cut Oracle: one targeted WAL write failure and one WAL sync failure inside a manually observed COMMIT. Trace one-shot failure and a bounded follow-on rollback/close-failure branch; never predetermine every injected error to mean rollback. Classify any execution without a proven COMMIT-phase hit as NOT TESTED for U3.

For this future subset, explicitly pin and record WAL, synchronous=FULL, effective pragmas and disabled automatic checkpointing, separating COMMIT I/O from checkpoint I/O. These are proposed experiment settings, not a production-default change. WAL commit and checkpoint are different operations, and FULL/NORMAL differ in per-commit sync. [WAL mechanics](https://www.sqlite.org/wal.html). Record native binary/DLL/source hashes, RunId, file identity/sidecar domain, process/nonce, operation/intent, original generation/epoch, callback causal sequence, error/state and actual settlement. No cross-process wall-clock-only attribution.

Failing before delegation is a controlled VFS denial. Partial delegation must describe actual changed bytes and VFS assumptions. Returning IOERR after a successful delegated sync is **injected lower-layer response loss**, not evidence that Windows FlushFileBuffers failed; classify it separately. Neither label proves physical uncertainty or universal power-loss safety. Do not require a predetermined unknown final cut for every fault: unknown is the caller's state until reliable reconciliation, not an invented SQLite durability outcome.

The future Oracle must validate one consistent all-old or all-new Event/Assertions/Provenance/History/versions/Snapshot-watermark/Cursor-coverage/ledger/receipt cut, intent/result/state digests and canonical stable identity. A mixed cut is FAIL; unreadable or contradictory authority is unavailable. Preserve error-time evidence before any potentially mutating SQLite recovery/checkpoint, with a reviewed complete DB/sidecar preservation procedure on the new disposable material. A main-file-only copy is not authority. Do not reopen original Recovery databases.

This minimum excludes control-COMMIT attribution, receipt-after-later-business-head, optional identity, multi-event Cursor, physical disk failure and production integration. Missing/superseded control nonce remains unknown; no historical control-receipt table is invented.

## 5. Settlement and fresh-connection reconciliation contract

1. On exceptional/unknown COMMIT revoke further writes, publication and ACK; record the original native result, intended operation and observable activity before cleanup. Serialize the connection and cancel queued candidates. Do not automatically rerun COMMIT or resubmit the bundle.
2. If still active, attempt explicit bounded rollback under retained valid Owner and record both errors plus subsequent activity. If inactive, that establishes only transaction activity, not successful COMMIT or trustworthy authority. SQLite's error responses must be observed, not assumed.
3. When rollback/state/close is unproved, quarantine the connection and instance: no subsequent business work and no intentional Owner release while the Project work could still commit. Actual successful handle destruction or an identity-bound owned experimental process exit can prevent that process's later COMMIT; neither proves the durable outcome or hidden physical-lock guarantees. Do not terminate a user's Host/process as production cleanup. SQLite close can return BUSY; close_v2 can defer destruction. [Native close semantics](https://www.sqlite.org/c3ref/close.html). The current Driver's normal close interface does not resolve genuine release-failure evidence gaps.
4. Begin outcome reconciliation only after settlement is established and same admitted resource/generation plus valid ownership are confirmed. Diagnostic reads while the old writer remains active cannot authorize an absence decision. New process/new uninjected connection reads a consistent healthy authority cut, original receipt/nonce/epoch, stable operation intent, canonical event and exact coverage. A newer legitimate recovery epoch does not invalidate a valid historical business receipt; it must not revive the old capability.
5. A complete matching receipt and consistent business cut confirms committed; publish current head and ACK only verified covered input under current ACTIVE authority/source protocol. Receipt absence alone never proves non-commit: require settled prior work, healthy complete authority, enforced same-transaction receipt invariant and the complete old cut. If business data is present without its required receipt, or nonce/intent/generation/cut contradicts, return unavailable; do not erase, rewrite or retry. Unreadable DB also remains unknown/unavailable. Snapshot alone is insufficient.
6. A controlled retry is permitted only for positively proven not-committed business work, unchanged stable operation/intent and expected base, valid current ownership/capability and supported input protocol. Existing Proposed limit: at most one bounded business retry. Conflicts, missing stable identity where cross-crash dedup would be needed, unknown outcome, corrupt evidence or failed fencing do not authorize replay. A same-transaction BUSY COMMIT retry in SQLite is a distinct documented path, not a general IOERR rule. No automatic failed-fencing-instance activation. External ACK cannot share SQLite atomicity.
