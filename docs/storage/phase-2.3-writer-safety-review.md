## 1. Safety model, meanings and assumptions

### 1.1 Separate authorization, exclusion and publication

- **Logical Project** is an independently allocated Core ProjectId, with a reviewed observation-root binding. It is not a filename, source Thread ID, VS Code Workspace, Git remote or file ID.
- **Owner coordination** is the actual lifetime transaction on one physical Owner resource for the binding, stable across generations. HELD_UNFENCED does not authorize business work.
- **Database authorization** requires the current generation/epoch/token and valid base to match inside the Project write transaction. A remembered token or local ACTIVE flag is insufficient.
- **Business modification** includes the complete applicable event/Assertion/correction/version/head/receipt/Snapshot/Cursor bundle, not just a fixture counter. Maintenance/control transitions must have their own reviewed checks; there is no unfenced SQL escape path.
- **Publication and ACK** occur outside SQLite. Their lifecycle and source-coverage conditions need separate arguments. Serializing SQL cannot make a UI update or external consumption acknowledgment atomic with Owner loss.

S1 below concerns one effective participating Writer authority over a logical Project, not merely one simultaneous SQLite transaction. Two stale local ACTIVE flags can coexist after invisible loss; two transactions taking turns is not proof that only one actor was authorized. S2 concerns durable modification order in one stable Project generation. It does not imply S3's immediate revocation after loss.

The initial proposed threat model is cooperative same-user APV participants on a reviewed local Windows x64 runtime/volume. It includes ordinary contention, observed lifecycle loss, process crash and returned errors needing fail-closed handling. It does not offer adversarial same-user SQL/file access protection or invisible broken-VFS safety. Excluding an undetectable fault requires explicit support-scope approval; exclusion cannot be inferred from a passing experiment or used to waive ordinary supported-environment errors.

## 2. Six separate Writer safety findings

### S1 — At most one effective Writer for one logical Project

- **Exact property:** at most one participating instance has valid lifetime Owner authority plus a confirmed current Project capability for business work in the admitted binding/generation. Do not equate this with at most one local ACTIVE flag or one SQL write lock.
- **Mechanism / premises:** same-resource Owner exclusion, HELD_UNFENCED → confirmed fencing → ACTIVE, private non-transferable capabilities and controlled release/loss (H1–H6). Contender B cannot become ACTIVE while A normally holds Owner; a handoff drains A before releasing that resource.
- **Admissible order:** A ACTIVE → intake revoked → Project finished/closed → Owner released → B obtains Owner → new epoch confirmed → B ACTIVE.
- **Counterexample / gap:** duplicate physical Owners can both be held. Hidden Owner loss can leave A believing it is ACTIVE while B acquires; before B fences, A's old epoch still matches. If both fence sequentially against one healthy Project DB, only the current epoch can pass each transaction, but logical intake/publication exclusivity and live flag uniqueness have not thereby been established. Sharing/copying one valid capability also defeats a Writer-identity claim even if SQLite serializes transactions.
- **Evidence:** OP01/02/03 prove their same-binding schedules; OP04 proves recorded takeover; OP09 has no real divergent-Owner competition. Production catalog/profile/lifetime cases remain pending.
- **Production Verdict:** **PROVABLE UNDER ASSUMPTIONS** for cooperative lifetime exclusivity under H1–H6; production compliance **NOT TESTED**. Unconditional logical exclusivity despite split identities or hidden loss is **NOT GUARANTEED**. S2 alone is not an S1 proof.

### S2 — No old-epoch business COMMIT after a newer epoch COMMIT

- **Exact property:** within one unchanged Project resource/generation, after fencing COMMIT `F(e+1,t2)`, a business transaction presenting `(e,t1)` cannot subsequently make a legal durable modification. The comparison is database commit order, not receipt timestamps, PID order, COMMIT invocation or ACK order.
- **Mechanism / premises:** fencing and business mutations acquire the same Project write resource and validate immutable presented capability inside it (the Project-resource portions of H2/H3, plus H4/H5). The two write transactions cannot overlap their exclusive intervals. This argument does not require Owner exclusion itself to remain healthy. Fencing does not merely update an independent Owner DB.
- **Admissible orders:** old data transaction completes before fencing; or fencing completes first and the later old transaction sees mismatch and rolls back. §3 gives the complete two-case argument.
- **Counterexample / gap:** checking before BEGIN, reusing a cached check after transaction end, bypassing token validation, restoring an old epoch, Project file replacement or split WAL/locking breaks premises. Copying the new token into an old instance is a forbidden new-authority path, not a valid old-capability retry.
- **Evidence:** OP05 stale-capability rejection and OP07 ordered handoff support subsets. OP07's interleaved A was already closed; neither it nor OP02 proves a still-live post-fencing stale transaction race in production. S13/full write-path audit remain NOT TESTED.
- **Production Verdict:** **PROVABLE UNDER ASSUMPTIONS** on the Project-specific H2/H3 and H4/H5 premises, **NOT TESTED** for enforcement on all production paths. An external Owner loss alone does **not** invalidate this conditional same-Project argument if Project identity/serialization remain sound. No unconditional guarantee when those premises fail.

### S3 — No old Writer COMMIT after Owner loss, before new fencing

- **Exact property:** after A actually loses Owner, no A business COMMIT is permitted even if the Project control row still contains A's epoch/token.
- **Mechanism / premises:** permanently revoke observed loss; final live-instance/connection guard and rollback; defer controlled release until Project completes (H6). Project epoch equality cannot independently establish continued Owner authority.
- **Admissible order:** controlled loss occurs before final guard → guard rejects → complete Project rollback → B fences after data lock release.
- **Counterexample / gap:** A owns Project transaction at e; Owner disappears; B obtains Owner but Project BEGIN is BUSY; A commits at e while new epoch is not yet committed. This is consistent with S2. Unsafe OP06 actually reproduces the controlled version. Hidden loss after final guard adds §3.3's unobservable window to the protected design.
- **Evidence:** OP06 protected/close/deferred covers observed rollback/close/normal release; it does not prove native invisible loss. P0 verifies no unfenced activation by the BUSY candidate, not instant cancellation of an older Writer.
- **Production Verdict:** **PROVABLE UNDER ASSUMPTIONS** for the controlled, observable lifecycle; **MITIGATED ONLY** by guards for broader native faults; unconditional immediate revocation is **NOT GUARANTEED**. Real Driver/API/OS failure paths **NOT TESTED**. Mandatory S3 under hidden external faults is an **ARCHITECTURAL BLOCKER** for this scheme.

### S4 — Detect/block external change between final guard and COMMIT

- **Exact property:** every relevant external Owner-state change after a successful final guard but before Project COMMIT is detected in time to prevent that COMMIT.
- **Mechanism / premises:** adjacent synchronous guard/COMMIT excludes application-controlled same-thread reentrancy. `.open`/`.inTransaction` is a connection-state observation, not an atomic Owner-and-Project operation or independent native lock attestation.
- **Admissible order:** ordinary release is queued until the data section has committed/rolled back; observed loss before the guard rejects it.
- **Counterexample / gap:** guard passes → hidden Owner loss/replacement → B acquires Owner but waits for Project lock → A COMMIT e → B fencing e+1. Even an added last Project token read cannot observe a fencing transaction that is still blocked. No synchronous JS adjacency excludes external OS/other-process action.
- **Evidence:** OP06/07 only support the recorded controlled lifetime schedules. No hidden final-window evidence exists; passing finite timing tests could not establish universal detection.
- **Production Verdict:** **MITIGATED ONLY** for cooperative lifecycle; external atomic detection/prevention **NOT GUARANTEED**. S2 remains intact in the counterexample while H2–H5 hold. Unconditional S4 requires another reviewed safety mechanism/failure model; it cannot be repaired by declaring epoch stronger.

### S5 — Logical and physical identity survive paths and lifecycle

- **Exact property:** all participants in one logical Project share the intended Owner resource and the intended active-generation Project database/WAL namespace; changed resources cannot reuse old authority as though unchanged.
- **Mechanism / premises:** unique catalog binding, independently allocated IDs, generation lifecycle, approved path and physical identity checks; existing-bound missing files block. H1/H2 must be established outside the Core.
- **Admissible order:** all entrants converge on one verified binding before acquisition; sanctioned maintenance under stable Owner retires old generation and closes data handles before reviewed replacement/new generation. Restart revalidates rather than derives identity from the supplied path.
- **Counterexample / gap:** split Owner + same healthy Project preserves S2 but loses same-Owner lifetime exclusion; same Owner + replaced Project invalidates S2 across the old/new resources; split both permits independent e/heads for the same claimed Project. Two hard-link names can share a main file without proving a common journal namespace. Path metadata checks can race later SQLite opens or COMMIT.
- **Evidence:** OP09 alias/copy input refusal, G2/G1 rejection, moved-file refusal and EBUSY mutation denial; no successful replacement, directory recreation or real different-lock-file competition. Fixture `dev/ino/birth` observations do not prove production handle binding.
- **Production Verdict:** current identity protection **MITIGATED ONLY**; full binding/admission **NOT TESTED**; successful external replacement/split-resource safety **NOT GUARANTEED**. Unresolved H1/H2 are P0 production blockers, not permissible guesses.

### S6 — Crash/unknown outcome/release error cannot create illegal effects

- **Exact property:** no uncommitted/unproved bundle is published/ACKed; reconciled identical operations do not create a second canonical mutation; retirement/unknown outcome does not revive old capability. Legitimate repeat ACK of proven covered input is not globally exactly-once delivery.
- **Mechanism / premises:** confirmed commit, stable operation intent/receipt, consistent full cut and safe transaction settlement before retry, then fresh valid Owner recovery (H1–H7). Full policy is Failure Contract F02/F10–F13.
- **Admissible orders:** pre-COMMIT crash → verified old cut; post-COMMIT/pre-ACK crash → new cut + matching receipt + no second canonical mutation, current owner reconciles coverage/current head.
- **Counterexample / gap:** unknown COMMIT → fresh Reader sees no receipt while old transaction is still capable of later COMMIT → blind replay; or close throws and old instance is revived. Another gap is external Owner loss after data COMMIT but before publication: SQL fencing alone cannot prevent a stale actor's UI/ACK action. A prior committed historical cut is not necessarily the current head. Source identity absence permits declared at-least-once input repeats, not universal dedup.
- **Evidence:** reinforced OP04 post has independent duplicate/O2 SQL and ACK checks; OP08 unknown is simulated after known epoch success. Real COMMIT I/O ambiguity, real release failures, full provenance/correction/Cursor recovery and production Host publication are NOT TESTED.
- **Production Verdict:** controlled fixture crash/retry subsets have PASS WITH LIMITATION; proposed verified-outcome semantics are **PROVABLE UNDER ASSUMPTIONS**, actual full enforcement **NOT TESTED**. Epoch alone only **MITIGATES** stale data authority, and unconditional publication/replay safety under hidden/identity/native faults is **NOT GUARANTEED**. Do not convert intent into an implementation PASS.

## 3. Project transaction ordering: derivation and counterexamples

### 3.1 Basis and conditional argument

SQLite documents one simultaneous write transaction, write serialization, and BEGIN IMMEDIATE acquisition. A stale WAL read snapshot cannot simply be promoted after a concurrent writer's commit. These are database premises, not APV production evidence. [SQLite isolation](https://www.sqlite.org/isolation.html), [transaction control](https://www.sqlite.org/lang_transaction.html).

Let `D(e)` be A's checked business transaction and `F(e+1)` B's checked control transaction on the **same healthy resource/generation**. Each exclusive write interval begins at successful BEGIN IMMEDIATE and ends at actual COMMIT/ROLLBACK. H4 puts the epoch read, validation, complete mutations and COMMIT in that interval; H5 prevents rollback/reuse of authority between successful takeovers.

There are two possible orders. If D acquires first, F cannot acquire its write interval before D ends. D's successful COMMIT is therefore before F's successful COMMIT. If F commits first, D's later acquired interval reads at least that current epoch, sees its presented old capability mismatch and must roll back. Thus no legal D(e) can COMMIT **after** F(e+1). A queued older candidate or a suspended process does not retain a Project write lock across that ordering by permission alone. This is a conditional reasoning argument, not a mechanized proof or a substitute for auditing actual writes.

No hidden check-to-COMMIT epoch race exists **inside that same correctly held Project write transaction**: B cannot install a newer epoch through a concurrent Project write while A holds it. The unresolved final gap is the independent Owner resource, or a violation of Project resource/lock premises. Last-guard failures in S3/S4 must not be presented as a refutation of conditional S2; S2 must not be presented as a proof of S3/S4.

### 3.2 Five required timings

| Timing                                    | Causal order, not cross-process wall clock                                                                                                                        | Conclusion / required response                                                                                                                                   |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1: A gets Project write lock first       | D BEGIN → read e/validate/mutate → B Owner acquired → F BEGIN waits/BUSY → D COMMIT or rollback → only then F BEGIN/update/COMMIT e+1                             | D may commit before fencing if Owner loss is invisible; it cannot commit after F. B remains unfenced; if its bounded attempt fails it must not ACTIVE/ACK        |
| T2: B fences first                        | F BEGIN/update/COMMIT e+1 → D BEGIN → row is e+1, presented e rejected → full rollback                                                                            | S2 holds; all prior tentative DML must roll back. If validation happened before D BEGIN instead, this argument is invalid                                        |
| T3: loss after final guard                | D BEGIN/read e/mutate → final Owner guard passes → external Owner loss → B obtains Owner/F BEGIN BUSY → D COMMIT e → F may later commit e+1                       | S3/S4 can fail, S2 still holds on healthy shared Project resource. No cross-file atomicity, no instantaneous revocation                                          |
| T4: new Writer's fencing BUSY             | B Owner HELD_UNFENCED → required Project BEGIN fails SQLITE_BUSY → B BLOCKED, no epoch/ACTIVE/WRITING/ACK → safe cleanup → later fresh actual acquisition/fencing | P0's 250 ms SQLite attempt and 5 s parent BLOCKED waiting watchdog are distinct; neither is a lease/preemption proof                                             |
| T5: old Writer writes again after fencing | D1 ends → F COMMIT e+1 → A still holds local old candidate/flag → D2 BEGIN → old e/token mismatch                                                                 | Reject and rollback D2, including checkpoint-only/maintenance paths where applicable. Never load/adopt new token as permission or retry an old cached validation |

COMMIT outcome uncertainty does not change actual serialization order; it changes what a caller may safely claim about that order. Reconciliation needs valid authority and a settled suspect transaction. A repeated COMMIT command after an error is not automatically a new valid transaction or an approved retry. Do not substitute a returned error, Worker exit or ACK timestamp for the actual committed cut.

### 3.3 Countermodels outside the premises

**C1: different Owners, one stable Project.** A holds O1 and e1. B holds O2 and installs e2 in shared P after A's data transaction ends. A's next checked data transaction is rejected, but A/B may both believe they own intake; subsequent reacquisition through split Owners can keep superseding epochs. Database serialization protects the conditional post-fence cut, not logical Owner uniqueness or availability. OP09 did not execute this competition.

**C2: split Project histories.** A's open P-old has G1/e1. The path is externally replaced/copied as P-new with the same marker/history; B opens P-new and fences e2. A can commit e1 on P-old after that wall-clock moment. There is no shared transaction order across P-old/P-new, so S2's same-resource premise is false. This is a design countermodel, not a newly observed Windows outcome or claim that the measured EBUSY operation succeeded. Ordinary aliases must also preserve WAL/SHM coordination; equal main-file identity is not enough.

**C3: receipt absence before transaction settlement.** A's COMMIT result is unknown and its transaction can still finish. A Reader's current cut has no receipt. Retrying from that observation before settling the suspect transaction is not proven safe. Fencing that actually commits on the same Project necessarily follows the prior write interval, but it does not independently settle catalog/generation errors or prove operation intent. Use F11's settlement and complete authority rules, not a time lease or one missing SELECT row.

**C4: uncooperative Writer.** An external process acquires SQLite's valid write lock but omits epoch checks or edits the control row. Serialization still exists; APV permission semantics do not. Neither stored tokens nor digests are access control against that actor. Such safety is not established by this proposal.

## 4. Project/Owner identity binding — Proposed rules and unresolved mechanics

### 4.1 Keep four identities separate

| Identity                                                    | Binding role                                                                                                                              | What it is not                                                                |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Core ProjectId                                              | Logical observed Project, allocated independently and preserved through reviewed lifecycle                                                | Path, volume/file ID, workspace object or Agent identity                      |
| Observation root identity + approved locator                | Private catalog lookup/convergence for the initially supported single known local root; aliases may converge only if actually established | Proof that copies/worktrees/same remote are the same logical Project          |
| Stable StoreKey + Owner incarnation                         | One coordination domain across the binding's generations; marker and actual resource identity checked                                     | A per-window/profile allocation or token granting business writes             |
| Active generation + Project incarnation + sidecar namespace | One authoritative Project history/fencing domain; retirement is durable                                                                   | A matching copied schema/marker/digest or a missing-file bootstrap permission |

Physical identifiers are admission evidence for a particular resource incarnation, not permanent Core IDs. A deleted/recreated root/file must not be silently adopted because a locator or recycled metadata matches. Approved generation transitions and revocation history remain necessary. Relocation/recreation is blocked pending the existing explicit lifecycle policy; this review adds no project-move feature.

### 4.3 Minimum binding sequence and P0 implementation feasibility gap

1. Host validates one private app root/catalog and the source observation root without writing APV state into user repositories. Resolve ambiguity before committing a binding; safe diagnostics exclude raw paths by default.
2. In a short catalog transaction, reuse or create one approved root binding/StoreKey. Recheck binding version/lifecycle after waiting; never keep a catalog transaction open while waiting for Owner. Initialization uses its existing `creating` state/recovery contract, not a cross-file atomicity claim.
3. Resolve/validate existing Owner identity, acquire its actual held transaction and recheck binding. Only an explicitly new creating binding may initialize resources under the reviewed creation protocol.
4. Open the bound Project generation under compatible sidecar/locking rules, validate identity/authority and recover; fence in its own write transaction. Only confirmed valid fencing permits ACTIVE.
5. On restart, maintenance and safe boundaries, revalidate. Any required unknown/mismatch revokes writes and returns unavailable; retain history, no new alternate lock. Metadata checks do not eliminate replacement after a check.

**Unresolved and not assumed:** the current Host/Driver contract has no reviewed method proving that its metadata observation and SQLite's actual open database correspond throughout the required lifetime. Harness `support.cjs` checks paths and `dev/ino/birth` metadata at boundaries; it does not inspect the Driver's actual database handle, detect all reparse/volume behaviors or pin a namespace atomically. `noLinks` uses lowercase comparison and does not explicitly enforce a production DB hard-link policy. These are evidence limits, not authorization to change the Harness or claims that prior fixture audits were false.

Before implementation, specify a practical reviewed metadata/open/lifetime strategy and its residual replacement exclusion. Candidate Windows handle APIs are **documentation-backed but APV integration NOT TESTED**; do not assume the JS Driver exposes the needed native handle. Separate metadata opens require review for sharing/locking side effects and still leave a TOCTOU interval. Prefer existing Host capabilities where sufficient; an unproven new native binding is not automatically required or selected. If necessary identity facts cannot be obtained, reject Writer admission. If strong protection against successful same-user replacement is required, that requirement cannot be met by periodic metadata checks and needs architecture review.

## 6. Unsupported and fail-closed boundary

Follow the existing Proposed Failure Contract; these are safety-boundary clarifications:

- Invalid/unproved logical binding, unknown file incarnation, split sidecar namespace, unsupported medium, schema/generation conflict or unreadable required identity: **no acquisition/business permission; unavailable/conflict**, not fallback allocation.
- Owner held but fencing BUSY/failed/unknown: **HELD_UNFENCED/BLOCKED, never ACTIVE/WRITING**. Watchdog affects observation/cleanup policy only; it grants no authority and cannot prove cancellation of a hung synchronous call.
- Observed Owner loss/release start/error: permanently disable the instance and prevent later queued work/publication/ACK; settle/close data before intentional Owner release. Real acquire/recovery/fresh fencing alone can authorize a different instance. Unknown native outcome is not a retained-lock proof.
- Unknown COMMIT/recovery: no guessed current state/receipt/ACK. Settle suspect work and reconcile exact intent/nonce/authority under valid ownership. Keep truthful last-known separate from successful current restoration.
- Hidden lock failure, successful external replacement, malicious protocol-bypassing SQL or dependency violation: **NOT GUARANTEED**. Reject detected instances/environments and preserve diagnostic evidence; do not promise reliable detection of invisible events. Unsupported exclusion requires explicit review and does not excuse a supported-environment error path.
- PID, heartbeat, timeout, absence from a process snapshot or a new path string never grants Owner. No force unlock, global cleanup, migration-reset, token copying or repeated close-as-revival.

Network storage and unsupported deployment restrictions remain proposals from the Failure Contract. No Windows production Host is declared supported here; cross-platform, power-loss and production shutdown/error behavior remain NOT TESTED.

## 9. Final bounded recommendation

**REVISE CURRENT PROPOSAL**, with the B + C interpretation and retained A resources/lifetime. Conditional same-Project fencing can establish S2; it cannot establish instantaneous Owner revocation S3/S4, logical uniqueness without binding, or safe publication/recovery by itself. The present unimplemented identity/open/lifetime and outcome contracts are **P0 production blockers**.

This is not KEEP CURRENT PROPOSAL unchanged: claims must be separated, binding mechanics resolved, write-path/publication obligations explicit and support/failure assumptions approved. It is not a blanket requirement for a new coordination framework: bounded cooperative support may retain the two-file design if these gates are met. **ARCHITECTURAL BLOCKER** applies if unconditional invisible-loss/final-window/replacement safety is required within support; broader assumptions cannot conceal that missing guarantee.

Only this Proposed review is added. Other design/Decision/acceptance changes are suggestions for the next architecture review, not executed edits. Core remains agent-neutral, Observer-only and independent from SQLite/Host/VS Code; the transaction bundle and original provenance/correction/unknown semantics remain intact. No new algorithm, experiment, Driver decision, production package or Git commit/push is performed. Await architecture review and separate authorization.
